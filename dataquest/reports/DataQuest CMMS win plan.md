# Turn Equinox into DQBH's dispatch brain

Equinox already covers most of the DQBH brief's platform requirements, so the team should spend every remaining hour on the **orchestration layer the brief actually scores**. That layer is missing today. Auth, RBAC, REST/OpenAPI, request intake and approval, websocket, email and push notifications, a workflow rules engine, shift-based capacity, analytics, maps, MinIO storage and a Gemini assistant all exist in the fork. What does not exist is **pre-approval validation, technician skills, ranked auto-assignment, spare-part reservation, an SLA/exception engine with instant reassignment, conflict checks on normal assignment, a supervisor verification step, and any populated work-order history**. In the code, `WorkOrderHistory` is rendered in the UI but never written, and `WORK_ORDER_OVERDUE` is still a `//TODO`. Leading FSM products (Salesforce Field Service, Dynamics 365, ServiceNow, Maximo, SAP FSM) all solve dispatch the same way: hard filters, then a weighted, explainable score, then booking. They treat dropout as "absence → unassign → re-rank". The team can copy that pattern in plain Spring/SQL in about a day of focused work. The winning demo is one story: Machine M-104 at Site A breaks, the platform validates, routes, reserves and notifies, then survives a technician dropout, a part shortage and an SLA breach live, and ends on a verified fix with a tamper-evident timeline. Two risks override everything else. A participant repo dates the finale **Oct 7–8, 2026, which means it may be under way right now**, and the event's rules on pre-existing open-source code are unknown, so AGPL disclosure must be explicit and upfront.

## Equinox covers the plumbing; the decisions between "create" and "complete" are missing

Equinox today handles the M-104 scenario as a pass-through. A user creates a Request, an admin clicks Approve, a work order is created with whatever assignee the request carried (or the approver, if `autoAssignRequests` is on), assignees are notified, and the technician logs labor, consumes parts and completes with a signature. **The system makes no decisions in between.** The table below maps each brief requirement to its status, with code evidence from branch `yg` (paths under `api/src/main/java/com/grash/` unless noted). I spot-checked the critical claims: there is no `new WorkOrderHistory`/`workOrderHistoryService.create` call anywhere, the `job/` folder has no SLA or overdue job, `WORK_ORDER_OVERDUE` is marked `//TODO`, and the parent POM is Spring Boot 3.5.16.

Test all four before relying on them in the demo.

## Industry leaders filter, score, explain, then re-rank on every exception

The big FSM vendors converge on one dispatch architecture, and the brief's language maps onto it almost word for word. Salesforce Field Service splits a scheduling policy into **work rules** (pass/fail filters such as Match Skills and availability) and **service objectives** (weighted grades such as ASAP, Minimize Travel, Minimize Overtime, Preferred Resource and Skill Level). Each objective is normalized so that, for example, the closest candidate scores 100 and the furthest 0, and the highest weighted sum is recommended ([Trailhead](https://trailhead.salesforce.com/content/learn/modules/field-service-lightning-scheduling-basics/examine-scheduling-policies)). Dynamics 365 models demand as a Requirement with required **characteristics** (skills with optional ratings), a territory, a time window and a duration. Its Schedule Assistant ranks matching resources by availability, skills and estimated travel time ([MS Learn URS](https://learn.microsoft.com/en-us/dynamics365/common-scheduler/developer/understanding-and-customizing-resource-matching-in-urs); [MS Learn Schedule Assistant](https://learn.microsoft.com/en-us/dynamics365/field-service/schedule-assistant)). ServiceNow assigns "by skills, parts, location, and availability" and **reassigns automatically when a technician runs late** ([ServiceNow Dynamic Scheduling](https://www.servicenow.com/products/dynamic-scheduling.html); [Dispatcher Workspace](https://www.servicenow.com/uk/products/dispatcher-workspace.html)). Maximo models labor as craft plus skill level against shift calendars and flags an assignment red when available hours can't cover it ([IBM Community](https://community.ibm.com/community/user/discussion/scheduler-application)). SAP FSM matches on skills, predicted duration, availability, location and priority through a no-code policy designer ([SAP](https://www.sap.com/products/scm/field-service-and-asset-management/features.html)). No vendor publishes default weights. The team should therefore present its weights as **tunable policy**, not as fixed numbers.

The remaining brief requirements have equally clear precedents. **Eligibility** in Salesforce is an Entitlement or AssetWarranty tied to an asset or service contract ([Salesforce FS Dev Guide](https://developer.salesforce.com/docs/atlas.en-us.field_service_dev.meta/field_service_dev/fsl_dev_soap_objects.htm)). **Approval** in UpKeep lets admins enrich a request before converting it, and a decline must carry a reason that goes back to the requester ([UpKeep Help](https://help.onupkeep.com/en/articles/9627833-how-administrators-and-limited-administrators-can-approve-and-manage-work-order-requests)). **SLA** follows ServiceNow's task-SLA model: start, pause and stop conditions, a breach time that moves later with pauses, and percentage thresholds (50/75/90%) that fire warnings ([ServiceNow Task SLA](https://www.servicenow.com/docs/r/MlbQAgTiiiMOLOw9T36wJg/IzrPpIJiB2a2oFdgpBOUEg); [ServiceNow Community](https://www.servicenow.com/community/hrsd-forum/trigger-sla-breach-for-50-and-75/m-p/3552790)). **Parts** follow Maximo, which creates reservations at APPR, subtracts hard reservations from the available balance, and flags BACKORDER when that balance goes negative ([IBM Support](https://www.ibm.com/support/pages/inventory-reservations); [ReliabilityWeb](https://reliabilityweb.com/tips/article/making_maximo_work_for_you)). **Exceptions** are mostly status semantics rather than special features. In Dynamics 365, a canceled booking returns the work order to Unscheduled ([MS Learn](https://learn.microsoft.com/en-us/dynamics365/field-service/work-order-status-booking-status)). Salesforce has "Cannot Complete", Maximo has WMATL, and Salesforce's ResourceAbsence object is how dropout is expressed ([Salesforce ResourceAbsence](https://developer.salesforce.com/docs/atlas.en-us.228.0.object_reference.meta/object_reference/sforce_api_objects_resourceabsence.htm)). **Verification** is a supervisor step after completion: Review/Approval in Dynamics 365 and Pending review in ServiceNow ([ServiceNow work order task states](https://www.servicenow.com/docs/r/DBkKvgbNn2vmEpXdLk9O2w/4V7ehAd~gF500f5YT0Fn4A)). Tractian makes photo and signature fields mandatory before closure ([Tractian FAQ](https://faq.tractian.com/en/articles/9171313-create-procedures)).

This shapes the algorithm choice. Technician dispatch is formally a workforce scheduling and routing problem ([Castillo-Salazar et al., Annals of OR 2016](https://eprints.nottingham.ac.uk/36529/)), but a **filter plus weighted greedy pick per request** is what Salesforce's "Candidates" and Dynamics' Schedule Assistant actually do for single jobs. That approach covers the brief. Timefold is the most Java-native optimizer, but it requires **JDK 21+, and its starter supports Spring Boot 4.x only** ([Timefold GitHub](https://github.com/TimefoldAI/timefold-solver); [Timefold Spring Boot docs](https://docs.timefold.ai/timefold-solver/latest/running-timefold-solver/library/spring-boot)). Equinox runs Java 17 on Boot 3.5, so Timefold belongs in the "future work" column. A batch "optimize backlog" button using the assignment problem (Hungarian method in about 100 lines, or OR-Tools CP-SAT) is a credible stretch goal ([OR-Tools assignment](https://developers.google.com/optimization/assignment/assignment_example)). It earns a pitch line: "greedy policy dispatch in real time, global optimization for the backlog, the same split Salesforce uses."

The scoring core should mirror the vendor pattern exactly. **Hard filters** remove anyone without every required skill, anyone off shift or with a `ShiftException` covering the job window, anyone not at the request's site (or outside a radius), and anyone whose `allocatedMinutes + estimatedDuration` exceeds `getUserCapacityForDay`. The **soft score** is a weighted sum of normalized factors: proximity `1 − d/d_max` (0.35), skill surplus (0.20), workload `1 − active/max` (0.20), earliest availability (0.15), and prior work on the same asset (0.10). For CRITICAL priority, shift weight toward proximity and earliest start, the way Salesforce runs separate emergency policies. Distance is haversine on `Location` lat/long, behind a `TravelTimeService` interface, with ETA ≈ km / 30 km/h. That avoids Google Distance Matrix billing and public-OSRM rate limits during a live demo ([OSRM table limits](https://rdrr.io/cran/osrm/man/osrmTable.html)). Store the top three backup candidates at assignment time so reassignment is instant. Re-validate them before use. If no candidate qualifies, relax radius, then the workload cap, then skill tier, and finally escalate as `UNASSIGNED_ESCALATED`.

Three design rules keep this coherent. First, route every status change through **one transition method** with an explicit allowed-transitions map (Maximo hard-codes these rules the same way in WOStatusHandler, per [IBM Support](https://supportcontent.ibm.com/support/pages/node/1112013)). That method writes history, publishes a Spring `ApplicationEvent`, and from there triggers notifications, webhooks, STOMP pushes and audit entries. Second, the SLA clock uses a hybrid design: event listeners start and stop clocks on transitions, and the one-minute job catches threshold crossings that happen with no record update. Warn at 75%, set `SLA_AT_RISK` at 90%, set `SLA_BREACHED` at 100%, and **never reset the clock on reassignment**. Third, demo seed targets for SLA (P1 response 1h / resolve 4h, P2 4h / 1 business day, and so on) are design choices, not sourced industry figures. Label them as configurable.

## Extensibility: two thin real hooks, everything else on one honest slide

The brief lists mobile, AI/ML, IoT, real-time, analytics, maps, blockchain and cloud. Judges reward a credible architecture plus **one or two working hooks**, not eight half-demos. Equinox's existing code makes several of these "already real", and the pitch should say so. The REST API with API keys, OpenAPI, webhooks, a Zapier controller and the workflow engine prove API-first integration. STOMP websockets prove real-time. The `StorageService` abstraction with `MinioService` and `GCPService` proves cloud-portable storage. The Gemini assistant with tool calling and a preview/confirm write step proves AI with deterministic enforcement. Meter readings with `WorkOrderMeterTrigger` already auto-create work orders, which makes them an IoT ingestion point.

Build only two new hooks. The first is a **hash-chained audit log**. Each row stores `sha256(prev_hash || canonical_json(event))`, a trigger blocks UPDATE and DELETE, and `/audit/verify` walks the chain. Tampering with a row in psql and watching "Verify" go red is a memorable moment. It is honest about scope: a hash chain is tamper-evident, not tamper-proof, because anyone with full DB access can recompute it unless the head hash is anchored externally ([the47network](https://the47network.com/blog/tamper-proof-audit-trail.html)). Anchoring via OpenTimestamps proves the hash existed by a given time, **not that the content is correct or who wrote it** ([dev.to OpenTimestamps](https://dev.to/neuportal/how-to-prove-a-prediction-was-made-before-the-event-with-opentimestamps-4p5d)). Say "blockchain-ready via a `LedgerAnchor` interface", never "runs on blockchain". Also avoid deprecated testnets: Polygon Mumbai was deprecated in April 2024 in favor of Amoy ([Alchemy](https://www.alchemy.com/blog/polygon-mumbai-testnet-deprecation.md)). The second hook is a **simulated IoT fault** that creates the M-104 request. A scripted POST to the existing readings endpoint is enough on stage. A Mosquitto container plus Spring Integration MQTT (`Mqttv5PahoMessageDrivenChannelAdapter`, with Paho added explicitly as an optional dependency) is the fuller version. Note that Mosquitto 2.x rejects anonymous clients by default, so it needs a config file with a listener ([Spring Integration MQTT](https://docs.spring.io/spring-integration/reference/mqtt.html); [Eclipse Mosquitto 2.0](https://projects.eclipse.org/node/20872)). This mirrors AWS's reference pattern, where an anomaly fires a Lambda that "creates work orders using the REST API of the target EAM or CMMS" ([AWS Guidance](https://aws.amazon.com/solutions/guidance/integrating-amazon-monitron-with-treon-connect-on-aws/)).

Everything else belongs on the architecture slide as design-only, marked plainly. **Mobile:** a PWA on the same API. The native app was removed in commit 58502dce, but Expo push support remains server-side. iOS web push requires iOS 16.4+ and a home-screen install ([OneSignal](https://documentation.onesignal.com/docs/en/web-push-for-ios)). **ML:** a FastAPI sidecar behind an `AiProvider` interface, trainable on NASA C-MAPSS or the Azure PdM dataset, which has machines, errors, maintenance and failures, the same entities as a CMMS ([C-MAPSS](https://github.com/ozogxyz/cmapss); [Microsoft Fabric PdM tutorial](https://learn.microsoft.com/en-ca/%20fabric/data-science/predictive-maintenance)). A useful talking point: Amazon Lookout for Equipment reached end of support on **7 Oct 2026**, the day the event began, which argues for owning a portable model over a managed one ([AWS](https://aws.amazon.com/lookout-for-equipment)). **Maps at scale:** Leaflet with OSM tiles. react-leaflet 5 needs React 19 and v4 needs React 18, so React 17 means vanilla Leaflet ([react-leaflet registry](https://tessl.io/registry/tessl/npm-react-leaflet)). PostGIS KNN via `<->` replaces haversine at scale ([PostGIS manual](https://postgis.net/docs/manual-3.7/es/geometry_distance_knn.html)). **Event backbone:** in-process domain events today, with an outbox (Spring Modulith 1.4.x on Boot 3.5; the 2.x line likely targets Boot 4, unverified) and externalization to Kafka as the scale-out path ([Spring Modulith events](https://docs.spring.io/spring-modulith/reference/1.3.0-SNAPSHOT/events.html)). **Cloud:** Compose profiles and Actuator health today, a Kubernetes diagram for later. State honestly what has to change before horizontal scaling: a STOMP broker relay, ShedLock on scheduled jobs, and idempotent event processing. Naming a known weakness raises scores ([DEV Community](https://dev.to/kurbaitaev/what-judges-actually-score-notes-from-a-year-of-hackathon-judging-3p4l)).

## The demo is M-104 surviving three failures in eight minutes

Indian hackathon rubrics typically weight innovation, technical implementation and impact at roughly 20–25% each, demo at 15–20% and completeness at 10–15%. They reward real data, quantified impact and a live demo that works first time ([Reskilll](https://blogs.reskilll.com/what-hackathon-judges-look-for-complete-judging-criteria-breakdown-2026/); [SIH FAQ](https://www.sih.gov.in/pdf/FAQs%20for%20SIH2019.pdf)). DataQuest's own rubric was not findable. ECDS is a data-science committee, so one genuinely working data element (SLA compliance, MTTR, or an explained match score) should be on screen. The atlas base wins "completeness". The orchestration layer has to win "technical".

The script runs about eight minutes. **0:00–0:30:** one-line identity: "the dispatch brain for industrial equipment service: from breakdown to verified fix, inside SLA, even when things go wrong." **0:30–1:15:** problem slide (calls, Excel, WhatsApp), followed immediately by the disclosure line: "Built on open-source Atlas CMMS (AGPL-3.0); in 24 hours we built validation, routing, reservation, the SLA/exception engine, the control tower and the audit chain." **1:15–6:30:** the live demo, in nine steps.

1. A simulated sensor alert, or a Site A supervisor, raises an urgent request for M-104 ("hydraulic pressure drop").
2. The validation checklist turns green: asset active, site matches, priority CRITICAL with a 4h SLA, hydraulics skill available, seal kit in stock.
3. The ops manager approves with one click. The ranked candidate list appears with per-factor reasons. The top technician is assigned, parts are reserved, and the notification lands on a phone.
4. On the technician view, the technician accepts, and the control tower updates live.
5. **Failure 1, dropout:** the technician is marked unavailable. A red exception appears, the next-best technician is assigned within seconds, the reservation transfers, and the history logs it.
6. **Failure 2, part short:** the seal kit is depleted. `PART_SHORTAGE` is raised and an auto-PO is drafted.
7. **Failure 3, SLA:** the time-warp turns the timer amber, then red, and an escalation fires.
8. Completion with checklist, photo and signature, then supervisor verify.
9. The M-104 timeline, followed by "Verify chain" going red after a psql tamper.

**6:30–7:15:** dashboard (SLA %, MTTR, open exceptions, utilization, site map). **7:15–7:45:** architecture slide, with built and designed items marked. **7:45–8:00:** impact claim, known limitation, and the identity line repeated.

Operational hygiene decides whether this works on stage. The demo control panel (dropout, deplete part, warp clock) has to be deterministic. Seed realistic data: 3 sites, about 15 assets, about 8 technicians with skills and shifts, one deliberately short part, and several weeks of history so charts aren't empty. Keep pre-logged browser profiles per role and run locally on Docker Compose with a hotspot backup. Have a **recorded video of the full flow**, because venue wifi fails often ([DEV Community](https://dev.to/kurbaitaev/what-judges-actually-score-notes-from-a-year-of-hackathon-judging-3p4l)). Rehearse three answers: "What did you build during the event?" (show event-window commits), "What breaks first at scale?" (reservation concurrency, handled with row locks; single-node STOMP broker) and "How is AI used?" (advisory scores, deterministic enforcement). Bitumen Supply Hub *may* be the DQBH sponsor. That is inferred from the code letters and not confirmed, but using plant-equipment language (pumps, heaters, decanters) costs nothing. One rival team is publicly building the same vision from scratch on FastAPI. Its README lists technician matching, an SLA/exception engine with dynamic reassignment, and an immutable "Service Passport", with setup "to be added later" ([DivyaaDharhsini/dataquest3.0](https://github.com/DivyaaDharhsini/dataquest3.0)). Equinox's advantage is that its whole lifecycle actually runs. Its liability is that judges can discount inherited code. Disclosure plus a sharply scoped "what we built" story addresses both.

## AGPL obligations and the risks that could sink the entry

Equinox is a rebranded fork of an AGPL-3.0 project, which creates concrete obligations. **Section 13** requires a network-accessible modified version to "prominently offer all users interacting with it remotely … an opportunity to receive the Corresponding Source" ([GNU AGPL-3.0](https://www.gnu.org/licenses/agpl-3.0.html)). **Section 5** requires prominent, dated modification notices, retention of the AGPL license for the whole work, and appropriate legal notices in interactive UIs. Section 7 permits terms that preserve author attribution and prohibit misrepresenting origin. Atlas is also dual-licensed, and its README reserves "white labeling, custom branding" (`LOGO_PATHS`, `BRAND_CONFIG`) for the **commercial license** ([Atlas CMMS GitHub](https://github.com/Grashjs/cmms)). Rebranding in source is less clear-cut than using the licensed config, but it does not cancel the attribution and non-misrepresentation duties. The minimum compliant posture has five parts:

- A public GitHub repo with full source and unsquashed history showing event-window commits.
- A README section naming Atlas CMMS, linking upstream, stating AGPL-3.0, and listing modified modules with dates.
- An "About / Source" link plus "Powered by Atlas CMMS" in the deployed UI footer.
- A disclosure slide early in the deck.
- Credit for AI tools used.

MLH-style rules forbid reusing earlier project code but allow public frameworks if they are listed in a README ([MLH guide](https://guide.mlh.com/general-information/judging-and-submissions/rules-for-your-hackathon)). Other events allow open-source bases but judge only new work, and can exclude teams that don't disclose ([UH CodeRED rules](https://github.com/UHCodeRED/rules)). **If DataQuest requires from-scratch work, an undisclosed fork risks disqualification**, so the team should ask organizers directly before pitching. None of this is legal advice.

The remaining risks rank as follows. **Timing:** the only dated source is a participant repo placing the finale at MG Auditorium, VIT Chennai, Oct 7–8, 2026 ([hellcat123git/dataquest](https://github.com/hellcat123git/dataquest)). Today is Oct 8, so the remaining window may be hours, not days. ## Conclusion

Everything else in the plan exists to make that moment, and the M-104 story around it, run reliably on stage.
