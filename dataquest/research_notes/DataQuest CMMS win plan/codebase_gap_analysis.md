# Equinox CMMS codebase vs. DataQuest 3.0 DQBH problem statement: gap analysis

All evidence comes from reading the code on branch `yg` (commit 74d1c01d). Paths are relative to `E:\cmms`. Backend package root is `api/src/main/java/com/grash` (written as `grash/` below).

## 1. Gap matrix (requirement by requirement)

### Takeaway
The fork already covers most of the "platform plumbing" (auth, RBAC, REST, OpenAPI, websocket notifications, email, push, webhooks, a workflow rules engine, analytics, file storage, an AI assistant). The DQBH-specific workflow is the weak part. There is no pre-approval validation (eligibility, skills, parts), no technician skills, no auto-routing by availability or location, no parts reservation, no SLA or exception engine, and the per-work-order history table is never written.

### Inferences
- Most of the problem statement maps to existing modules. Judges will mainly look at the **core workflow differentiators**: validation before approval (#6), skill/availability/location routing (#8, #9, #11), parts reservation (#12), and the exception engine with reassignment (#14). All four are missing or only partial, so they are the highest-value build targets.
- The existing `WorkloadService` (shift capacity plus overlap search) and `ShiftConfiguration` are an unusually good base for availability-aware routing and conflict detection. The new code mostly needs to call them from new places.
- The empty `WorkOrderHistory` is a cheap, high-visibility fix. The UI already renders history entries as system comments, so populating them immediately gives the "timeline / audit history" deliverable.

### Gaps
- I did not verify whether the frontend WO detail page renders the history/comments feed for every role, or whether Google Maps needs an API key at runtime (the Map component exists but the key config was not checked).
- I did not inspect `RequestPortal` field types fully or `WorkOrderConfiguration`/`FieldConfiguration`, which may let priority, asset or location be marked required on forms. That would be partial "validation" at the UI level.
- `WorkflowService.runRequest` was only partially read. The absence of `case APPROVE` is inferred from the listed switch cases (ADD_CHECKLIST, SEND_REMINDER_EMAIL, ASSIGN_TEAM/USER/ASSET/CATEGORY/LOCATION/PRIORITY).
- I did not check whether the license gates (`licenseService.hasEntitlement` for SIGNATURE_CAPTURE, LOW_STOCK_ALERTS, VOICE_NOTES) are enabled in the self-hosted build. If they are not, signature and low-stock alerts may be blocked in the demo. Worth testing.

## 2. Request lifecycle, technicians, parts, SLA: how the M-104 scenario runs today

### Takeaway
Today the M-104 scenario runs as: create Request (asset M-104, location Site A, priority HIGH) → admin clicks Approve → WO created with whatever assignee was on the request (or the approver, if auto-assign is on) → assignees get in-app, websocket, push and email notifications → technician logs labor, consumes parts (stock decrements, 406 if insufficient), completes with signature and feedback. The system makes no decisions in between (validation, matching, reservation, escalation).

### Cited Findings
- Request creation does no domain validation — [RequestService.create](api/src/main/java/com/grash/service/RequestService.java) (lines 100-150).
- Approval creates the WO, auto-assigns the approver only — [RequestService.approve / createWorkOrderFromRequest](api/src/main/java/com/grash/service/RequestService.java) (lines 194-206, 373-435); flag in [GeneralPreferences](api/src/main/java/com/grash/model/GeneralPreferences.java) (`autoAssignWorkOrders`, `autoAssignRequests`).
- Capacity and overlap conflict detection exist only in the workload scheduler — [WorkloadService.scheduleWorkOrder / getUserCapacityForDay](api/src/main/java/com/grash/service/WorkloadService.java) (lines 144-275).
- Part stock is checked only at consumption time — [PartService.consumePart](api/src/main/java/com/grash/service/PartService.java) (lines 146-200).
- No SLA, overdue or escalation job — [job/](api/src/main/java/com/grash/job/); TODO in [WebhookEvent](api/src/main/java/com/grash/model/enums/webhook/WebhookEvent.java).
- Completion checks only the signature — [WorkOrderService.changeStatus](api/src/main/java/com/grash/service/WorkOrderService.java) (line 833+).

### Inferences
Recommended minimal build order for the hackathon demo, ranked by impact per effort:
1. **Populate WorkOrderHistory** (about 1 hour): history calls in create, patch, changeStatus, approve and reassign. This gives an instant timeline in the existing UI.
2. **Skills plus required skill** (about 3 hours): `Skill` entity, `User.skills`, `WorkOrderBase.requiredSkills` (this also covers Request), one Liquibase changeset, multiselects.
3. **Pre-approval validation** (about 3 hours): `GET /requests/{id}/validation` returns the checks (asset operational, site match, priority set, a skilled technician available at the site today via `getUserCapacityForDay`, parts in stock). Show it as a green/red checklist in `RequestDetails.tsx`; block approve unless the checks pass or are overridden.
4. **Auto-assign best technician** (about 4 hours): rank users by skill match, same site (`User.location`/`Location.workers`), remaining capacity (WorkloadService) and haversine distance. Call it on approve, then auto-schedule with `WorkloadService.scheduleWorkOrder`.
5. **Parts reservation** (about 3 hours): `Part.reservedQuantity`, `Request.requiredParts`, reserve on approve, convert on complete, release on cancel. A shortage raises an exception and an auto-PO.
6. **Exception engine plus SLA job plus reassign** (about 5 hours): `WorkOrderException` entity, Quartz `SlaMonitorJob` (pattern: `LdapSyncJobScheduler`), `SlaPolicy` per priority (add CRITICAL), alerts via `NotificationService.createMultiple` plus websocket plus the `WORK_ORDER_OVERDUE` webhook, `POST /work-orders/{id}/reassign`, and a "Mark unavailable" button for technician dropout that sets a ShiftException to 0 minutes and triggers reassignment.
7. **Operations control tower page** (about 4 hours): pending requests, active WOs, open exceptions, technician load bars (`/workload/overview`), site map (existing Map component), live via websocket.
8. **Verification step** (about 1 hour): `verifiedBy`/`verifiedOn` plus `PATCH /work-orders/{id}/verify`; block COMPLETE with incomplete tasks.
9. Stretch: AI dispatcher tool in `AssistantTools` (suggest technician, explain exception), a simulated IoT reading creating the M-104 request, and hash-chained audit log for the "blockchain-ready" story.

### Gaps
- Effort estimates are my own judgement, not measured.
- I did not check the existing test suite (api/src/test) for regression coverage of RequestService and WorkOrderService.
